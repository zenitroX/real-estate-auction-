# SKANDX Multi-Instance Readiness & Scalability Assessment

**Document ID:** `ENG-ARCH-004`  
**Classification:** Technical Architecture & Scalability Review  
**Target Environment:** Staging, Canary, and Multi-Replica Horizontal Scaling  
**Last Updated:** November 2026  
**Auditor:** Principal Backend Architect & Distributed Systems Engineer  

---

## 1. Architectural Scope & Thesis

This document investigates the behavior of the SKANDX backend when scaled horizontally from **1 container instance** (current staging/canary baseline) to **$N$ container instances** behind a load balancer (such as Nginx, AWS ALB, or GCP Cloud Run).

### Key Architectural Finding
> [!NOTE]
> The current in-process architecture is **100% safe and optimal for single-instance staging and canary deployments**. Introducing Redis immediately is anti-pattern over-engineering (violating the Ponytail principle) until distributed multi-replica workloads are deployed. However, before scaling to $N \ge 2$ production replicas, three specific stateful components require explicit architectural handling.

## 2. Multi-Instance Behavioral Analysis

| Subsystem | Single Instance (Current) | Multi-Instance ($N \ge 2$) Behavior | Consequence & Severity | Remediation Strategy |
| :--- | :--- | :--- | :--- | :--- |
| **Admin Authentication (HMAC)** | In-process HMAC verification with timestamp. | **Fully Stateless & Multi-Instance Safe**. As long as `ADMIN_JWT_SECRET` is identical across all containers, any replica can verify tokens generated by any other replica. | **`SAFE`** (No change needed) | Keep stateless HMAC with shared secret. |
| **Admin Login Rate Limiter** | In-memory sliding window dictionary (`_login_rate_limits`) with `threading.Lock()`. | Limits are isolated per container. Total login attempts across $N$ instances equals $N \times 5$ attempts per minute under round-robin. | **`LOW`** (Acceptable for $N \le 3$, prevents single-node DDoS) | Nginx IP-hash sticky routing OR Redis sliding window if $N > 3$. |
| **Contact Lead Rate Limiter** | In-memory sliding window dictionary (`_contact_rate_limits`). | Effective limit is $N \times 15$ submissions per minute per IP. | **`LOW`** | Nginx `limit_req_zone` at reverse proxy layer handles edge throttling before reaching containers. |
| **Circuit Breaker** | Process-local state machine (`CLOSED`, `OPEN`, `HALF-OPEN`). | Each container independently monitors Supabase health. Container A tripping `OPEN` does not force Container B `OPEN`. | **`POSITIVE / SAFE`** (Graceful partial degradation; localized network blips do not cascade) | Maintain localized circuit breakers. |
| **Auction Listings Cache** | In-memory dictionary `_cache` with 300s TTL. | Container A clearing cache on update does not invalidate Container B. Users might see stale data for up to 300s. | **`MEDIUM`** | Reduce TTL to 60s, or use HTTP ETag / Cache-Control validation at Nginx edge. |
| **Scraper Execution Lock** | Process-local boolean `_crawler_running` and `_crawler_lock`. | If `/api/scrape/trigger` is invoked on Container A and Container B simultaneously, both will spawn scrapers concurrently. | **`HIGH`** (Risk of duplicate database writes and IP bans from auction portals) | Implement PostgreSQL Advisory Lock (`pg_try_advisory_lock`) in Supabase. |
| **Buyer Lead Persistence** | Appended to `data/leads.jsonl` on disk + Supabase sync. | In ephemeral multi-container clusters, local JSONL files are split across instances. | **`MEDIUM`** (Supabase must be authoritative; ephemeral disk is only WAL) | Supabase is authoritative (`load_leads()` queries Supabase first). |

## 3. Detailed Component Evaluations

### 3.1 Scraper Execution: The Concurrent Crawler Risk
In `backend/app.py`:
```python
_crawler_lock = threading.Lock()
_crawler_running = False
```
- **The Problem:** In a multi-replica setup, two requests to `/api/scrape/trigger` routed to different containers will both acquire their local `_crawler_lock`. Both will spawn browser/HTTP crawlers against bank auction portals simultaneously.
- **The Solution (PostgreSQL Advisory Locks):**
  Instead of requiring Redis, use native PostgreSQL advisory locks built directly into PostgreSQL/Supabase:
  ```python
  # Zero-dependency distributed locking via Supabase PostgreSQL
  def acquire_distributed_crawler_lock():
      # Lock ID 982341 (arbitrary 64-bit int representing crawler)
      result = supabase.rpc("try_advisory_lock", {"lock_id": 982341}).execute()
      return result.data is True
  ```
  This eliminates multi-instance race conditions with **zero additional infrastructure**.

### 3.2 Edge Rate Limiting vs Centralized Redis
Rather than adding Redis to manage 5-15 requests per minute, the production Nginx reverse proxy handles rate limiting at the ingress layer:

```nginx
# deploy/nginx.conf (Ingress Edge Rate Limiting)
limit_req_zone $binary_remote_addr zone=api_login_limit:10m rate=5r/m;
limit_req_zone $binary_remote_addr zone=api_contact_limit:10m rate=15r/m;

server {
    location = /api/admin/login {
        limit_req zone=api_login_limit burst=2 nodelay;
        proxy_pass http://skandx_backend_upstream;
    }

    location = /api/contact {
        limit_req zone=api_contact_limit burst=5 nodelay;
        proxy_pass http://skandx_backend_upstream;
    }
}
```
**Advantage:** Malicious brute-force attacks and volumetric traffic are dropped at the Nginx edge without consuming Python application threads or database connections.

## 4. Redis Decision Threshold Matrix

| Deployment Stage | Replicas | Concurrency | Architecture Recommendation | Redis Required? |
| :--- | :--- | :--- | :--- | :--- |
| **Staging** | 1 | $\le 25$ | Single container + in-process locks + Nginx | **NO** |
| **Canary** | 1 | $\le 50$ | Single container + in-process locks + Nginx | **NO** |
| **Production Baseline** | 2 | $\le 100$ | 2 containers + Nginx IP-hash + Postgres Advisory Locks | **NO** |
| **Production Scale** | $\ge 4$ | $> 250$ | Multi-AZ Kubernetes / ECS + Redis Cache & Distributed Lock | **YES** |

---

## 5. Summary Recommendation

For the immediate Staging and Canary phases:
1. **Maintain zero-Redis simplicity**: In-memory rate limiting and stateless HMAC tokens are fully sufficient.
2. **Add PostgreSQL Advisory Lock** to `/api/scrape/trigger` before provisioning 2 or more replicas.
3. **Mount persistent volume or rely on Supabase as primary lead store** so container destruction does not orphan local JSONL logs.
